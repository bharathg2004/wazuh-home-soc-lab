# Incident Report: SSH Brute-Force Attempt (Simulated)

**Status:** Resolved (test/training exercise — no real harm, scoped to an owned lab account)
**Severity:** Low (test environment) / would be **High** in a production context, since the attack culminated in a successful login
**Date:** 2026-11-23
**Analyst:** Bharath G

## 1. Summary

A simulated SSH brute-force attack was run against a throwaway test account (`labtarget`) on the `bharath-ubuntu-wsl` host, using Hydra with a small password wordlist. Wazuh detected the failed login attempts and the eventual successful login in real time. The built-in correlation rule for "multiple authentication failures" did not fire, because the attack (5 attempts) stayed under its default threshold of 8. A custom detection rule was subsequently written, debugged, and validated to close this gap.

## 2. Detection

| Time (UTC) | Event | Wazuh Rule | Level | MITRE ATT&CK |
|---|---|---|---|---|
| 12:37:02 | Failed login attempt #1 (`labtarget`) | 5760 — sshd authentication failed | 5 | T1110.001, T1021.004 |
| 12:37:04–12:37:20 | Failed login attempts #2–#5 | 5760 (x4) | 5 | T1110.001, T1021.004 |
| 12:37:21 | **Successful login** with password `Password123` | 5715 — sshd authentication success | 3 | T1078, T1021 |

Alerts were generated by Wazuh's default ruleset without any custom configuration — the agent on the target host (`bharath-ubuntu-wsl`, ID 003) forwarded the relevant `sshd`/PAM log lines via journald, and the manager's stock decoders and rules classified them correctly.

## 3. Triage

- **Source:** 127.0.0.1 (same host — a deliberate lab constraint, since the attack tool and target shared one machine)
- **Target account:** `labtarget`, a disposable local account created specifically for this test, with no real privileges or data
- **Attack tool:** Hydra v9.6
- **Gap identified:** the built-in correlation rule (ID 5720, "sshd: Multiple authentication failures") requires 8 failures within its window by default. This test's 5 failures never crossed that threshold, so no higher-severity "this looks like a brute force" alert was raised — only the individual low-level failure alerts.

## 4. Containment / Response

Since this was a controlled test:
- The test account `labtarget` is local and disposable; no production credentials were involved
- In a real incident, the response at this point would be: disable or reset the compromised account, review what the attacker did after logging in, and check for lateral movement

## 5. Detection Gap Closed (Custom Rule)

A custom correlation rule (`rules/local_rules.xml`, ID `100010`) was written to lower the detection threshold from 8 to **3 failed logins within 2 minutes from the same source** — a more realistic early-warning threshold for a small environment.

**First attempt did not work.** The rule used `if_matched_sid` pointing at a parent rule ID (`5716`, the generic "authentication failed" rule). Despite being syntactically valid and confirmed loaded via the Wazuh API, it never fired — because the manager's correlation engine only counts the *exact* rule ID that produced the alert (the more specific child rule, `5760`), not its ancestor. Pointing the custom rule at `5760` directly fixed it; a controlled re-test (3 timed failed logins) confirmed the alert fired at the precise second the third failure occurred.

## 6. Lessons Learned

1. **Default thresholds are not automatically appropriate.** An 8-failure threshold may suit a high-traffic server, but is far too loose for a small environment where even a handful of failed logins from one source is notable.
2. **"The rule is loaded" and "the rule will fire" are different claims.** A syntactically valid, correctly-loaded correlation rule can still silently fail to trigger due to how rule ID matching actually works internally — always validate with a live, timed test, not just configuration review.
3. **Successful logins deserve attention too, not just failures.** The default ruleset correctly flagged the successful login (rule 5715) as a distinct, lower-severity event — in a real incident, correlating "many failures immediately followed by one success from the same source" is a strong brute-force-success indicator worth its own dedicated rule in a future iteration of this lab.
